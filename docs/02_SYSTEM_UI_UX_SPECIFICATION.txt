================================================================================
1. DESIGN PRINCIPLES
================================================================================

1.1 Design Reduces Work, Not Decorates
    The purpose of design here is not visual appeal. It is reducing the
    effort required to complete real business work (TP-059). Beautiful
    software that slows a shop owner down has failed.

1.2 Minimum Typing
    Typing on a low-end phone, often one-handed, often while serving a
    customer, is the single largest source of friction. Every screen must
    be evaluated on how much typing it demands.

    Required patterns:
        - Repeat-order instead of re-entering an order.
        - Select from previous values instead of free text.
        - Numeric keypads for numeric fields, always.
        - Sensible defaults pre-filled from history.
        - Contact picker instead of typing phone numbers.

1.3 Minimum Taps
    Core daily actions must be reachable within one or two taps from Home
    (TP-061). Specifically: place a repeat order, record a credit sale,
    confirm a delivery.

1.4 Offline Aware By Default
    Assume connectivity will fail mid-action (TP-062). The user should
    rarely have to think about it. See Section 12.

1.5 Familiar Over Novel
    Interfaces should resemble the workflows users already run on paper
    and WhatsApp (TP-063). A Loan Book screen should feel like a credit
    book. An Order Queue should feel like a list of outstanding jobs.
    Technology adapts to people, not the reverse.

1.6 Every Screen Justifies Itself
    Every screen must solve a clearly identified business problem
    (TP-064). Screens without measurable operational value should not
    exist.

1.7 Accessibility
    Legible type, adequate touch targets, sufficient contrast, screen
    reader support. Baseline, not enhancement.

================================================================================
2. MOBILE UX GUIDELINES
================================================================================

2.1 Device Reality
    Design and test against the realistic low end, not flagship devices:
        - Small screens (360dp width baseline)
        - Limited RAM and slower CPUs
        - Intermittent 3G / patchy data
        - Limited or expensive data bundles
        - Users with limited digital experience

2.2 Performance Budget
    - App startup should reach a usable screen fast; avoid blocking the
      first render on network calls.
    - Prefer cached data on first paint, then refresh.
    - Avoid heavy animation and large images on list screens.
    - Paginate every list; never load unbounded history.

2.3 Bandwidth Discipline
    - Request only what a screen needs.
    - Compress and lazily load images; never block a screen on them.
    - Cache aggressively; refetch only when meaningfully stale.

2.4 Touch Targets
    Minimum 44x44dp. Primary daily actions should be larger and placed
    within comfortable one-handed reach (lower half of the screen).

2.5 Navigation Pattern
    Bottom tab navigation (5 tabs) per role, with stack navigation for
    drill-down. Already implemented; unchanged.

2.6 Feedback & Confirmation
    Destructive or high-consequence actions (cancel order, decline order,
    delete Loan Book entry) require explicit confirmation.

2.7 Loading, Empty, Error States
    Every data-driven screen defines all three. Empty states should
    explain the next useful action, not merely state emptiness.

================================================================================
3. NAVIGATION STRUCTURE
================================================================================

3.1 Business Tabs
    Home | Account | Community | Discover | More

3.2 Supplier Tabs
    Home | Account | Community | Discover | More

3.3 Header Behaviour
    Top-level tabs use a persistent branded header showing context plus
    notification and profile access. Detail screens use a back-navigation
    header with a contextual title.

================================================================================
4. TYPOGRAPHY
================================================================================

    Display        28sp / Bold      Key figures (outstanding balance)
    Heading 1      22sp / Semibold  Screen titles
    Heading 2      18sp / Semibold  Section headers, card titles
    Body           15sp / Regular   Primary content
    Body Small     13sp / Regular   Secondary/supporting text
    Caption        11sp / Medium    Labels, timestamps, badges

Line height approximately 1.4x font size for body text. OS-level dynamic
font scaling must be supported without breaking layout.

================================================================================
5. COLOR PALETTE
================================================================================

Functional roles, implemented in frontend/mobile/src/theme/colors.ts:

    Primary          TruePoint Blue -- primary actions, active tab
    Primary Dark      Pressed/active states
    Secondary        Emerald Green -- supporting actions, positive states
    Success           Verified, completed, settled, positive trends
    Warning           Pending, awaiting action, attention needed
    Danger            Declined, cancelled, overdue, destructive actions
    Neutral 900-100   Text and surface greyscale
    Surface           Card and screen background
    Border            Dividers, card outlines, input borders

Status colour usage must be consistent across both roles so that
recognisable trust and status cues form over time. Colour is never the
sole indicator of status -- always paired with an icon and a text label.

================================================================================
6. COMPONENTS (VISUAL RULES)
================================================================================

Full technical definitions are in Document 03. Visual rules:

    - Cards share one corner radius, elevation, and padding rhythm.
    - Content hierarchy is predictable: identifier at top, supporting
      metadata in the middle, status or action trailing.
    - Status is always icon + colour + text.
    - Money amounts use a consistent format and are visually emphasised
      wherever they represent an outstanding obligation.

================================================================================
7. CARDS
================================================================================

Consistent radius, elevation, internal padding, and content hierarchy
across Order Cards, Supplier Cards, Loan Book Entry Cards, Customer
Cards, and Statistic Cards.

================================================================================
8. BUTTONS
================================================================================

    Primary        Solid fill -- the single most important action.
    Secondary      Outlined -- supporting actions.
    Tertiary       Text only -- low-emphasis actions.
    Destructive    Danger role -- cancel, decline, delete only.

One Primary button per screen or per card context.

================================================================================
9. FORMS
================================================================================

    - Labels always visible above the input, never placeholder-only.
      Users with limited digital experience lose placeholder context the
      moment they begin typing.
    - Inline validation errors beneath the relevant field.
    - Correct keyboard type per field, always.
    - Multi-step forms show a visible step indicator.
    - Minimise required fields ruthlessly. Every additional required
      field measurably reduces completion.

================================================================================
10. ICONS
================================================================================

One icon set throughout (lucide-react-native, implemented). Navigation
icons always pair with text labels -- icons alone are not sufficient for
first-time or less digitally experienced users.

================================================================================
11. LAYOUT & SPACING
================================================================================

8-point spacing scale (implemented in theme/spacing.ts):
    xs 4 | sm 8 | md 16 | lg 24 | xl 32 | xxl 48

Screen horizontal padding: 16dp baseline. Section spacing: 24dp.

================================================================================
12. OFFLINE & CONNECTIVITY UX
================================================================================

12.1 Connectivity Indicator
    A slim, persistent, non-blocking banner when offline. Never a modal.
    Never blocks work.

12.2 Read Behaviour Offline
    Cached data remains visible and usable: My Suppliers, recent orders,
    Loan Book entries and balances.

12.3 Write Behaviour Offline
    Actions are accepted and queued locally, with clear per-item state:
        Pending sync -> Synced -> Failed (with retry)

    The user must always be able to tell what has actually reached the
    supplier and what has not. This distinction is critical: a business
    must never believe an order was placed when it was not.

12.4 Sync Behaviour
    Automatic on reconnect, in the background, without user action.
    Conflicts surface as explicit, resolvable items rather than silent
    overwrites.

================================================================================
13. ANIMATIONS
================================================================================

Purposeful and brief (150-250ms). Standard platform transitions. Subtle
loading skeletons rather than spinners where content shape is known.
Animation must never delay a completed action, and must degrade gracefully
on low-end devices.

================================================================================
14. ACCESSIBILITY
================================================================================

    - Minimum 4.5:1 contrast for body text.
    - Accessible labels on all interactive elements.
    - Dynamic font scaling supported.
    - Colour never the sole status indicator.
    - Language: plain, direct, jargon-free. Avoid financial terminology
      where an ordinary word will do.
