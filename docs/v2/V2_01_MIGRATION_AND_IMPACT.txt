===========================================================================
PART 1 — THE FINDING THAT SHRINKS THIS
===========================================================================

The Product/Offer split sounded like a rewrite. It is not.

There are EXACTLY SIX foreign keys into `supplier.products` in the entire
backend:

  Reference                                              Becomes
  ─────────────────────────────────────────────────────  ────────
  network/orders/models/stock_order.py:357               OFFER
  supplier/inventory/models/inventory.py:54              OFFER
  supplier/supplier_profile/models/supplier_storefront.py:126   OFFER
  supplier/supplier_profile/models/supplier_profile_pin.py:42   OFFER
  network/connections/models/supplier_report.py:70       OFFER
  supplier/products/models/product_media.py:28           SPLITS

Five of six become Offer. One splits (catalogue images on the Product,
supplier's own photos on the Offer).

WHY THIS MATTERS

V1's `Product` model already IS an Offer. It carries `supplier_profile_id`,
`price_cents`, `compare_at_price_cents`, `sku`, `product_code`, `is_archived`.
It was correctly built and incorrectly named.

So the migration is:

  1. RENAME  supplier.products → supplier.supplier_offers
             Every existing FK already points at the right concept.

  2. ADD     catalogue.products (shared, brand, barcode, pack size, image)

  3. ADD     one NULLABLE product_id on the Offer, populated by matching

Step 3 is what makes it shippable. An unmatched Offer behaves exactly as it
does today. Nothing breaks on day one and the catalogue can be empty.

This is a two-week migration rather than a six-month rewrite, and it is only
true because the FK surface was kept this narrow. That is a V1 achievement.

PART 4 — MIGRATION ORDER
===========================================================================

The FK rename touches six tables, so it goes first and alone.

  STEP 1  RENAME + CAPABILITIES                      DONE 2026-09-08
          products → supplier_offers. Capability columns.
          Migration b1c2d3e4f5a6.

          GATE MET: 617 tests green (304 supplier+architecture, 313
          network) -- identical to the v1.0.0 baseline. No test needed a
          change beyond a symbol rename.

          SCOPE, and what was deliberately left alone. Renamed: the
          table, the Product model class -> SupplierOffer,
          ProductRepository -> SupplierOfferRepository, their two files,
          the six FK targets, and the table's own indexes and unique
          constraints. NOT renamed: the domain folder, services, schemas,
          API routes, JSON keys, or the ProductCategory / ProductUnit
          enums.

          The API is untouched ON PURPOSE. The mobile app is a shipped
          client calling /api/v1/supplier-discovery/products; renaming
          routes or response keys would break it for a rename that is
          internal. Verified after migrating: 26 product routes still
          registered, 18 blueprints.

          The two enums keep their names because they describe the
          CATALOGUE concept, not the offer, and will move to the
          catalogue domain in step 2 rather than being renamed twice.

          VERIFIED AGAINST THE DEV DATABASE, not just the suite, because
          conftest builds from metadata and never runs a migration -- a
          wrong migration passes every test. Checked directly: old table
          gone, model columns == database columns exactly, indexes and
          constraints renamed, all six inbound FKs intact, 53 offer rows
          preserved, capability defaults backfilled. The downgrade was
          run too, and re-upgraded: both directions preserve all 53 rows.

  STEP 2  CATALOGUE TABLE + NULLABLE product_id       DONE 2026-09-08
          Migration 9abc21f6810f.

          New area src/domains/catalogue/products/ with two models:
          Brand (name, slug, mark_url) and Product (name,
          normalized_name, brand_id, category, unit_quantity,
          unit_measure, gtin, image_url). supplier_offers gains a
          NULLABLE product_id.

          BRAND IS A TABLE, NOT A STRING, decided up front because
          migrating away from a string column is the expensive one. Two
          things need it: matching narrows candidates by brand before
          comparing names, and a free-text column yields "Coca-Cola",
          "Coca Cola" and "COKE" as three brands; and the image cascade
          (V2_00 2.8) resolves through a brand mark, which needs
          somewhere to live.

          THE TAXONOMY MOVED, THE POSTGRES TYPES DID NOT. ProductCategory
          and ProductUnit are now defined in
          catalogue/products/models/taxonomy.py -- a category is a fact
          about a product, not about one supplier's offer of it, and
          leaving them in supplier would have forced catalogue to import
          from supplier, which is backwards. supplier_offer.py
          re-exports them, so all fifteen existing import sites keep
          working unchanged and the diff stayed small. The Postgres
          TYPES stay in the supplier schema: moving a type between
          schemas means recreating it and rewriting every dependent
          column, which is real risk on live data for a cosmetic gain.
          They move when the catalogue becomes authoritative for
          categories, in that same change.

          DORMANCY IS TESTED, NOT ASSERTED. The safety argument for this
          step is "an unmatched offer behaves exactly as before", so the
          first test creates an offer the ordinary way and asserts
          product_id is null and harmless. Six tests: dormancy,
          matching, two suppliers sharing one product, duplicate GTIN
          rejected, barcodeless products allowed and not colliding, and
          SET-NULL-not-CASCADE on catalogue deletion.

          VERIFIED AGAINST THE DEV DATABASE: both catalogue tables match
          model metadata exactly (all five BaseModel columns present),
          the FK carries confdeltype 'n' (SET NULL), and all 53 existing
          offers are unmatched -- genuinely dormant. Downgrade drops the
          schema and the column and re-upgrade restores them, 53 rows
          preserved throughout.

          TRAP HIT AND RECORDED: the first revision id chosen collided
          with an existing migration (c2d3e4f5a6b7, already used by
          loan_book_tables), producing "Multiple head revisions". This
          project hand-writes sequential-looking hex revision ids rather
          than using alembic's generated ones, so collisions are likely
          -- grep the versions directory before assigning one. An audit
          of all 54 migrations found no other duplicates.

  STEP 3  IMPORT STAGING + UPSERT                     DONE 2026-09-08
          Migration 38197be69f75.

          THE BUG WAS MEASURED BEFORE IT WAS FIXED, and it was worse
          than "duplicates". A throwaway probe ran the same file twice
          and found create-only broke in TWO different ways:

            with SKUs in the file -- every row collided with the unique
            constraint on (supplier_profile_id, sku), so the second
            import created 0 offers and returned one error per row
            reading "SKU is already used by another product". A
            supplier's correct weekly price file was rejected wholesale
            and the message blamed them for their own data.

            without SKUs -- silent duplicates. "Coca-Cola 2L" twice,
            SKU-000001 and SKU-000002.

          THE UPSERT KEY IS THE SUPPLIER'S OWN SKU, because it is the
          only stable identity they control. A row whose SKU already
          belongs to one of their offers updates that offer in place --
          same row, same id, so orders, inventory, storefront sections
          and pins all stay attached.

          A ROW WITH NO SKU STILL CREATES, and that is recorded as an
          honest limit rather than a gap. Nothing in a blank-SKU row
          says WHICH existing offer it means; matching on name would be
          a guess and a wrong guess overwrites a real price. The
          supplier controls this by including their SKU column.

          A REPEAT SKU INSIDE ONE FILE IS STILL AN ERROR. An existing
          test caught this gap in the first implementation: two rows in
          the same file sharing a SKU would have had the first create
          and the second silently overwrite it, losing a line without
          telling anyone. "This SKU exists from last week" and "this SKU
          appears twice in the file I just sent" are different things
          and only the first is an update.

          import_rows records the outcome of EVERY row -- created,
          updated or failed, with the offer it produced -- so the report
          can name the lines that changed rather than only counting
          them. It is also the seam the preview gate and API ingestion
          land in later; neither exists yet and neither will need a
          second staging concept.

          THE FLOW DID NOT CHANGE. Still upload-then-process, no preview
          gate, because that is a UI change and the mobile app is a
          shipped client. The table is what makes the gate possible
          later without another migration.

          SECOND BUG FOUND AND FIXED: error_rows was frozen at the
          parse-time figure and never counted rows that failed at SAVE
          time, so a job could report 0 errors while its own report
          listed two. Recounted at the end.

          DELIBERATELY NOT DONE: FULL_CATALOGUE vs PARTIAL_UPDATE
          deletion semantics. Deciding what a row's ABSENCE from this
          week's file means needs a supplier-facing choice, and guessing
          wrong silently deletes a catalogue. Its own step.

          630 tests green (317 supplier + architecture + catalogue,
          313 network) -- the 623 baseline plus these 7.

          Verified on the dev database: import_rows columns match model
          metadata exactly with all five BaseModel columns, both FKs
          present with confdeltype 'n' on supplier_offer_id (SET NULL,
          so deleting an offer never erases how it got there). Downgrade
          and re-upgrade clean, 53 offers preserved.

  STEP 4  CONNECTION GATE REMOVAL
          The deletion pass. Own commit. Careful test pass.

  STEP 5  PAYMENT PATH SPLIT
          Direct → request. Digital → purchase.

  STEP 6  MATCHING AGENT
          Behind the confidence gate. Column mapping first (one call per
          file), per-row extraction second.

  STEP 7  WEB PORTAL AUTH + API KEYS

Steps 1 and 2 are safe to start immediately. Step 4 is the one that deletes
code and deserves the most care.

  KNOWN ENVIRONMENT NOTES
    pytest needs TEST_DATABASE_URL, SECRET_KEY, JWT_SECRET_KEY exported
    manually — Flask's CLI auto-loads .env but pytest does not.

    Do NOT run multiple large domain dirs in one pytest invocation. A ~10-min
    combined run exhausts the Postgres connection pool and produces a wall of
    phantom setup errors. Run one domain dir at a time.

    `flask db migrate` autogenerate surfaces unrelated pre-existing drift.
    Hand-trim generated migrations to the intended change only.

    BaseModel has FIVE columns: id, created_at, updated_at, is_deleted,
    deleted_at. A hand-written migration that omits deleted_at will pass tests
    (conftest uses db.create_all from metadata and never runs migrations) and
    fail in production. This happened once already; see migration
    f2345678901a.


===========================================================================
PART 6 — RULES FOR THE V2 WORK
===========================================================================

  1. Do not change approved work while refactoring next to it.
     This was violated once in V1 and cost a full revert. Consistency nobody
     asked for is not a reason to touch a working screen.

  2. Rank in SQL, not Python. Python sorting breaks under pagination.

  3. Tri-state booleans: null is not false.

  4. A thin rail is a broken rail. Under the minimum, render nothing.

  5. Unknown section types render nothing — the server can add a section
     without an app release.

  6. Silence is the honest answer. A section with no data does not appear.

  7. "App boots" proves imports, not that view functions run. Smoke-test the
     actual route.

  8. Never run a write smoke test against the dev database.

  9. Keep the long narrative comments current rather than deleting them. They
     are why V2 could be planned at all.
