===========================================================================
PART 1 — THE FINDING THAT SHRINKS THIS
===========================================================================

The Product/Offer split sounded like a rewrite. It is not.

There are EXACTLY SIX foreign keys into `supplier.products` in the entire
backend:

  Reference                                              Becomes
  ─────────────────────────────────────────────────────  ────────
  network/orders/models/stock_order.py:357               OFFER
  supplier/inventory/models/inventory.py:54              OFFER
  supplier/supplier_profile/models/supplier_storefront.py:126   OFFER
  supplier/supplier_profile/models/supplier_profile_pin.py:42   OFFER
  network/connections/models/supplier_report.py:70       OFFER
  supplier/products/models/product_media.py:28           SPLITS

Five of six become Offer. One splits (catalogue images on the Product,
supplier's own photos on the Offer).

WHY THIS MATTERS

V1's `Product` model already IS an Offer. It carries `supplier_profile_id`,
`price_cents`, `compare_at_price_cents`, `sku`, `product_code`, `is_archived`.
It was correctly built and incorrectly named.

So the migration is:

  1. RENAME  supplier.products → supplier.supplier_offers
             Every existing FK already points at the right concept.

  2. ADD     catalogue.products (shared, brand, barcode, pack size, image)

  3. ADD     one NULLABLE product_id on the Offer, populated by matching

Step 3 is what makes it shippable. An unmatched Offer behaves exactly as it
does today. Nothing breaks on day one and the catalogue can be empty.

This is a two-week migration rather than a six-month rewrite, and it is only
true because the FK surface was kept this narrow. That is a V1 achievement.

PART 4 — MIGRATION ORDER
===========================================================================

The FK rename touches six tables, so it goes first and alone.

  STEP 1  RENAME + CAPABILITIES                      DONE 2026-09-08
          products → supplier_offers. Capability columns.
          Migration b1c2d3e4f5a6.

          GATE MET: 617 tests green (304 supplier+architecture, 313
          network) -- identical to the v1.0.0 baseline. No test needed a
          change beyond a symbol rename.

          SCOPE, and what was deliberately left alone. Renamed: the
          table, the Product model class -> SupplierOffer,
          ProductRepository -> SupplierOfferRepository, their two files,
          the six FK targets, and the table's own indexes and unique
          constraints. NOT renamed: the domain folder, services, schemas,
          API routes, JSON keys, or the ProductCategory / ProductUnit
          enums.

          The API is untouched ON PURPOSE. The mobile app is a shipped
          client calling /api/v1/supplier-discovery/products; renaming
          routes or response keys would break it for a rename that is
          internal. Verified after migrating: 26 product routes still
          registered, 18 blueprints.

          The two enums keep their names because they describe the
          CATALOGUE concept, not the offer, and will move to the
          catalogue domain in step 2 rather than being renamed twice.

          VERIFIED AGAINST THE DEV DATABASE, not just the suite, because
          conftest builds from metadata and never runs a migration -- a
          wrong migration passes every test. Checked directly: old table
          gone, model columns == database columns exactly, indexes and
          constraints renamed, all six inbound FKs intact, 53 offer rows
          preserved, capability defaults backfilled. The downgrade was
          run too, and re-upgraded: both directions preserve all 53 rows.

  STEP 2  CATALOGUE TABLE + NULLABLE product_id       DONE 2026-09-08
          Migration 9abc21f6810f.

          New area src/domains/catalogue/products/ with two models:
          Brand (name, slug, mark_url) and Product (name,
          normalized_name, brand_id, category, unit_quantity,
          unit_measure, gtin, image_url). supplier_offers gains a
          NULLABLE product_id.

          BRAND IS A TABLE, NOT A STRING, decided up front because
          migrating away from a string column is the expensive one. Two
          things need it: matching narrows candidates by brand before
          comparing names, and a free-text column yields "Coca-Cola",
          "Coca Cola" and "COKE" as three brands; and the image cascade
          (V2_00 2.8) resolves through a brand mark, which needs
          somewhere to live.

          THE TAXONOMY MOVED, THE POSTGRES TYPES DID NOT. ProductCategory
          and ProductUnit are now defined in
          catalogue/products/models/taxonomy.py -- a category is a fact
          about a product, not about one supplier's offer of it, and
          leaving them in supplier would have forced catalogue to import
          from supplier, which is backwards. supplier_offer.py
          re-exports them, so all fifteen existing import sites keep
          working unchanged and the diff stayed small. The Postgres
          TYPES stay in the supplier schema: moving a type between
          schemas means recreating it and rewriting every dependent
          column, which is real risk on live data for a cosmetic gain.
          They move when the catalogue becomes authoritative for
          categories, in that same change.

          DORMANCY IS TESTED, NOT ASSERTED. The safety argument for this
          step is "an unmatched offer behaves exactly as before", so the
          first test creates an offer the ordinary way and asserts
          product_id is null and harmless. Six tests: dormancy,
          matching, two suppliers sharing one product, duplicate GTIN
          rejected, barcodeless products allowed and not colliding, and
          SET-NULL-not-CASCADE on catalogue deletion.

          VERIFIED AGAINST THE DEV DATABASE: both catalogue tables match
          model metadata exactly (all five BaseModel columns present),
          the FK carries confdeltype 'n' (SET NULL), and all 53 existing
          offers are unmatched -- genuinely dormant. Downgrade drops the
          schema and the column and re-upgrade restores them, 53 rows
          preserved throughout.

          TRAP HIT AND RECORDED: the first revision id chosen collided
          with an existing migration (c2d3e4f5a6b7, already used by
          loan_book_tables), producing "Multiple head revisions". This
          project hand-writes sequential-looking hex revision ids rather
          than using alembic's generated ones, so collisions are likely
          -- grep the versions directory before assigning one. An audit
          of all 54 migrations found no other duplicates.

  STEP 3  IMPORT STAGING + UPSERT                     DONE 2026-09-08
          Migration 38197be69f75.

          THE BUG WAS MEASURED BEFORE IT WAS FIXED, and it was worse
          than "duplicates". A throwaway probe ran the same file twice
          and found create-only broke in TWO different ways:

            with SKUs in the file -- every row collided with the unique
            constraint on (supplier_profile_id, sku), so the second
            import created 0 offers and returned one error per row
            reading "SKU is already used by another product". A
            supplier's correct weekly price file was rejected wholesale
            and the message blamed them for their own data.

            without SKUs -- silent duplicates. "Coca-Cola 2L" twice,
            SKU-000001 and SKU-000002.

          THE UPSERT KEY IS THE SUPPLIER'S OWN SKU, because it is the
          only stable identity they control. A row whose SKU already
          belongs to one of their offers updates that offer in place --
          same row, same id, so orders, inventory, storefront sections
          and pins all stay attached.

          A ROW WITH NO SKU STILL CREATES, and that is recorded as an
          honest limit rather than a gap. Nothing in a blank-SKU row
          says WHICH existing offer it means; matching on name would be
          a guess and a wrong guess overwrites a real price. The
          supplier controls this by including their SKU column.

          A REPEAT SKU INSIDE ONE FILE IS STILL AN ERROR. An existing
          test caught this gap in the first implementation: two rows in
          the same file sharing a SKU would have had the first create
          and the second silently overwrite it, losing a line without
          telling anyone. "This SKU exists from last week" and "this SKU
          appears twice in the file I just sent" are different things
          and only the first is an update.

          import_rows records the outcome of EVERY row -- created,
          updated or failed, with the offer it produced -- so the report
          can name the lines that changed rather than only counting
          them. It is also the seam the preview gate and API ingestion
          land in later; neither exists yet and neither will need a
          second staging concept.

          THE FLOW DID NOT CHANGE. Still upload-then-process, no preview
          gate, because that is a UI change and the mobile app is a
          shipped client. The table is what makes the gate possible
          later without another migration.

          SECOND BUG FOUND AND FIXED: error_rows was frozen at the
          parse-time figure and never counted rows that failed at SAVE
          time, so a job could report 0 errors while its own report
          listed two. Recounted at the end.

          DELIBERATELY NOT DONE: FULL_CATALOGUE vs PARTIAL_UPDATE
          deletion semantics. Deciding what a row's ABSENCE from this
          week's file means needs a supplier-facing choice, and guessing
          wrong silently deletes a catalogue. Its own step.

          630 tests green (317 supplier + architecture + catalogue,
          313 network) -- the 623 baseline plus these 7.

          Verified on the dev database: import_rows columns match model
          metadata exactly with all five BaseModel columns, both FKs
          present with confdeltype 'n' on supplier_offer_id (SET NULL,
          so deleting an offer never erases how it got there). Downgrade
          and re-upgrade clean, 53 offers preserved.

  STEP 4  CONNECTION GATE REMOVAL                     DONE 2026-09-08
          No migration -- requires_connection already shipped in step 1.

          THIS WAS NOT A DELETION PASS, and the earlier plan calling it
          one was wrong. The mobile app actively calls the
          connection-request endpoints
          (find-supplier/services/httpSupplierSearchService.ts, the
          supplier-side customer-requests screens). Deleting them would
          break a shipped client for a change that is supposed to make
          the platform MORE usable.

          So connection did not die -- it stopped being compulsory.
          requires_connection defaults FALSE, and a supplier who
          genuinely wants to approve businesses before stock moves turns
          it on and gets exactly the old behaviour. Request, approve,
          decline and disconnect all still work.

          THE RULE WAS WRITTEN OUT TWICE, WHICH IS THE REAL FINDING.
          ordering_gate.can_place_order had one copy and
          checkout_service.submit_checkout had another, independent one.
          Flipping only the gate would have left the app saying "you can
          order" on the product screen and then refusing at checkout
          with "send a connection request first" -- incoherent, and
          worse than the old behaviour which was merely strict. Both now
          call ordering_gate.connection_requirement_met, one definition.

          AN AUDIT CONFIRMED THOSE WERE THE ONLY TWO ACTION GATES. Every
          other ConnectionRequestStatus.ACTIVE check in the codebase is
          either the connection lifecycle itself (request_service,
          connection_list_service) or VISIBILITY -- whether a photo,
          contact details or collection address is shown, driven by the
          supplier's own photo_visibility / share_contact_details
          settings.

          VISIBILITY WAS DELIBERATELY LEFT ALONE, and this is a consent
          decision rather than a technical one. A supplier who set
          share_contact_details=true was agreeing that CONNECTED
          businesses could see their number. Flipping that to "anyone"
          would silently change what they consented to. It needs a
          supplier-facing re-consent, not a code change.

          ONE GAP THIS CREATED, AND HOW IT IS COVERED. Ordering opened
          up, so a business can now buy from a supplier it never
          connected to -- and it cannot collect from an address it
          cannot see. cart_service already returns the collection
          address on the cart, which is a genuinely narrow exposure (it
          takes a real cart with that supplier, not browsing), so the
          collect flow still works. The PROFILE endpoint's address gate
          stays as it is, per the consent reasoning above.

          can_place_order also gained a requiresConnection key so a
          client can tell "you may just order" apart from "this supplier
          approves buyers first" -- additive, and the mobile app ignores
          fields it does not know. It also now raises SupplierNotFound
          for a supplier that does not exist; it previously imported
          SupplierProfileRepository without ever calling it and reported
          SUPPLIER_HAS_NO_PRODUCTS instead, which was true and useless.

          Tests: three gate tests and three checkout tests encoded the
          old mandatory rule and were rescoped to requires_connection
          =True rather than deleted -- including the disconnect-and-
          re-request regression, which came from a real reported log and
          still matters for an opt-in supplier. Two new tests state the
          behaviour change directly at both layers.

          632 tests green (315 network, 317 supplier + architecture +
          catalogue) -- the 630 baseline plus these 2.

  STEP 5  PAYMENT PATH SPLIT                          DONE 2026-09-08
          No migration -- the database already had everything.

          THE RULE WAS ALREADY THE DESIGN. StockOrderStatus's own
          docstring already said a verified gateway payment "needs no
          supplier approval at all", and CheckoutOutcome already carried
          order_status so the provider decides it. Step 5 was therefore
          not about inventing the rule; it was about making it ASKABLE
          in one place instead of implied in several.

          THE BUG THIS SURFACED. DIRECT replaced CASH and
          PROOF_OF_PAYMENT as the single off-platform method. It was
          added to the order enum and to the Postgres type -- and to
          NOTHING ELSE:

            checkout_schemas.py       OneOf([CASH, PROOF_OF_PAYMENT,
                                      PAYFAST]) -- rejected "DIRECT"
                                      outright, above the service layer
            providers/composition.py  enumerated CASH and
                                      PROOF_OF_PAYMENT by hand, so
                                      DIRECT fell through to
                                      PaymentProviderNotConfiguredError
            manual_provider.py        no DIRECT branch
            stock_order_payment.py    db.Enum listed three values; the
                                      database itself already had four

          The backend could not complete a DIRECT checkout at all.

          LATENT, NOT LIVE. The mobile app still sends CASH and
          PROOF_OF_PAYMENT -- its PaymentMethod type does not include
          DIRECT -- so no business hit it. It would have broken on the
          day the frontend switched over, which is the obvious next step
          of the work that introduced DIRECT.

          WHY NOTHING CAUGHT IT, which matters more than the bug. Tests
          exercised DIRECT only on the REJECTION path, where the
          spending cap fires before a provider is ever reached. A
          successful DIRECT checkout had never once been run. Two of the
          three faults also lived ABOVE the service layer, and the
          orders suite tests services directly, never routes.

          THE FIX IS ONE DEFINITION: DIRECT_PAYMENT_METHODS and
          is_direct_payment() in models/stock_order.py, beside the enum.
          Composition, checkout_service's two tuples and the payment
          repository all ask it rather than listing. Same shape as step
          4's connection rule, and the same root cause: a rule written
          out N times drifts at the first change.

          VERIFIED BY BREAKING IT. The old hand-written list was
          restored temporarily and three tests failed, including the
          HTTP one returning the exact error a real user would have
          seen: "Must be one of: CASH, PROOF_OF_PAYMENT, PAYFAST."
          Restored, all ten pass.

          The new test file goes through the HTTP ROUTE, not the
          service, precisely because that is where two of the faults
          were.

          642 tests green (325 network, 317 supplier + architecture +
          catalogue) -- the 632 baseline plus these 10.

  STEP 6  MATCHING -- SPLIT INTO FREE AND PAID, AND RE-ORDERED

    6a  THE FREE TIERS                                DONE 2026-09-08
        Migration c32c5e454643.
        Barcode, learned alias, normalised exact, rules + pg_trgm. The
        confidence gate, the alias table, the review queue. No model, no
        key, no cost, and nothing depends on the paid tier ever being
        switched on.

    6b  THE PROVIDER SEAM                             DONE 2026-09-08
        Migration 2876c4df29c3.
        AIProvider, FakeAIProvider, ClaudeAIProvider, composition, and
        the decision ledger that makes the budget ceiling real. Three
        independent guards each default closed. Exactly one file imports
        a vendor SDK, enforced by an AST architecture test.

    6e  CSV COLUMNS + WIRING                          DONE 2026-09-08
        No migration -- the columns are read, not stored separately.

        DONE BEFORE 6c/6d ON PURPOSE, and the reasoning is the point.
        The obvious order was to build the paid tier next. But the
        matcher was not connected to anything -- propose_match existed
        and nothing called it -- and the CSV could not carry a barcode,
        so tier 0, the free and certain rung, was unreachable from a
        real import.

        Building the paid tier first would have meant paying for a model
        without knowing what fraction of rows reaches it. This order
        produces that number instead.

        THE CANONICAL FIELD SET (bulk_import/fields.py) defines the
        import contract once. The CSV parser derives its required and
        known column lists from it, and the future API push will derive
        its request schema from the same place. Written now because this
        codebase has hit "the same rule written out N times" TWICE in
        consecutive steps -- the connection gate in step 4, the payment
        rail in step 5 -- and the API adapter is not written yet, so
        this was the last cheap moment.

        FOUR NEW COLUMNS, ALL OPTIONAL: barcode, brand, pack_quantity,
        pack_unit. Optional because a required column added today breaks
        every template a supplier already has, for no gain they asked
        for. A test asserts an old-style file still imports unchanged.

        barcode is the one that matters commercially: an exact GTIN
        match is a database lookup, so every row carrying one is matched
        free, forever. The supplier-facing help text says so plainly,
        which aligns their effort with the platform's bill.

        A REAL GAP CLOSED: unit_quantity/unit_measure existed on the
        model and on the single-product form but NO import could set
        them, so a supplier with 3,000 pack products had to enter pack
        sizes one at a time by hand.

        A REAL BUG FOUND BY A TEST: with MATCHING_ENABLED=false,
        propose_match returned confidence 0.0 -- indistinguishable from
        "no plausible candidate" -- so the gate said CREATE_NEW and the
        KILL SWITCH QUIETLY FILLED THE CATALOGUE with a new product for
        every imported row. "Off" and "found nothing" must not share a
        representation. Fixed with MatchDecision.SKIPPED and a check
        before anything is proposed.

        Matching runs inside the import and can never fail it. An
        unmatched offer is exactly how every offer behaved before the
        catalogue existed, so a matching problem costs the supplier
        nothing -- their products are already saved when it runs.

    6g  FREE-TIER IMPROVEMENTS, MEASURED             DONE 2026-09-08
        No migration.

        THE MEASUREMENT THAT DROVE IT. Two realistic SA wholesaler files
        were run through the ladder: supplier A (clean names, barcodes)
        builds a 25-product catalogue, supplier B is a DIFFERENT
        wholesaler whose export shares almost no phrasing -- 30 rows, of
        which 25 should match and 5 are genuinely new.

        Reading the misses was the whole exercise. NONE were ambiguous.
        Every one was shorthand or a spelling difference:

          W/STAR SUPER MAIZE          White Star
          SIMBA S&V CHIPS             Salt & Vinegar
          5 ROSES TEA                 Five Roses
          SUNLIGHT DISHWASH LIQ       Dishwashing Liquid
          COLGATE TOOTHPASTE          Colgate REGULAR Toothpaste
          SPRITE 2 LITRE              Sprite 2L

        THREE FREE FIXES, EACH RE-MEASURED ON THE SAME FILE:

          abbreviation dictionary        40% -> 60%
          containment + ambiguity guard  60% -> 72%
          measure canonicalisation       72% -> 80%

        AND THE SHAPE MATTERS MORE THAN THE NUMBER. At 80%, CREATE_NEW
        is exactly 5 -- precisely the five genuinely new products, and
        nothing spurious. Every one of the 20 auto-links was checked
        against the catalogue by hand and is correct. ZERO WRONG LINKS
        at any stage of the three iterations. The 5 rows left in review
        are correct matches sitting between 0.71 and 0.91, which a
        person clears in seconds.

        CONTAINMENT NEEDED A GUARD, and that is the one genuinely
        subtle piece. "Every word the supplier wrote appears in the
        catalogue name" is strong evidence -- and "Coca-Cola 2L" is
        equally a subset of "Coca-Cola Original 2L" and "Coca-Cola Zero
        2L". So the bonus is paired with an ambiguity check: when the
        top two candidates score within 0.05 the proposal is flagged
        contested and goes to review regardless of how high it scored.
        Flagged rather than scored down, because "94% sure" and "94%
        sure about each of two products" are different facts and folding
        one into the other loses the reason.

        WHAT THIS SAYS ABOUT THE PAID TIER. Tier 4 would now see 20% of
        matchable rows rather than 60%. It is still worth building for
        the genuine tail, but it should never have been paid to work out
        that S&V means salt and vinegar. Every future entry in the
        abbreviation dictionary or the brand alias table shrinks the
        paid tier permanently, at no running cost.

        The measurement script is throwaway (scratchpad, not committed)
        and ran against the dev database inside a transaction that
        rolled back -- catalogue 0 rows before and after.

    6c  EXTRACTION (job A)                            NOT BUILT
    6d  ADJUDICATION (job B)                          NOT BUILT

  STEP 7  WEB PORTAL AUTH + API KEYS                  DONE 2026-09-08
        Migration a51f7fb3e75e.

        THE ONE LINE THAT MADE IT CHEAP
          JWT_TOKEN_LOCATION went from ["headers"] to
          ["headers", "cookies"]. flask_jwt_extended then reads the
          token from whichever location a request actually carries, so
          @fully_authenticated, @role_required and @verified_required
          serve the app and the portal unchanged. Adding "cookies" does
          not make cookies required. There was no mobile-facing change
          in the whole step, and three tests assert exactly that.

        WHAT WAS BUILT
          /api/v1/auth/web/{login,refresh,logout,session}, a SECOND
          blueprint beside the mobile one rather than flags inside it.
          The shipped app's /auth routes were not edited.

          Cookies: httpOnly + Secure + SameSite=Lax. The refresh pair is
          scoped to Path=/api/v1/auth/web so the long-lived credential
          is not attached to ordinary API calls. Max-age is passed
          explicitly, because the library's default writes a SESSION
          cookie (gone on browser close) that has nothing to do with the
          token's real 7-day life.

          CSRF: flask_jwt_extended's double-submit, NOT hand-rolled.
          Enforced only on cookie-borne requests, so bearer callers
          never see it. Two CSRF cookies exist and are not
          interchangeable -- csrf_refresh_token for /refresh and
          /logout, csrf_access_token everywhere else. Sending the wrong
          one 401s in a way that reads exactly like an expired session.

          CORS: Flask-Cors, scoped to /api/v1/*, explicit origin
          allowlist from WEB_ORIGINS, supports_credentials=True. Never
          "*" -- browsers refuse credentialed requests to a wildcard, so
          a wildcard breaks the portal rather than loosening it.
          X-CSRF-TOKEN had to be allowed explicitly; it is not
          CORS-safelisted, so without it every portal write dies at
          preflight.

          Session lifetime: 30 min access / 7 day refresh, separate env
          vars from mobile's 15 min / 30 days. Carried as a
          session_kind claim on the token so a refresh renews the kind
          of session it actually is, rather than trusting the caller.

          Role routing: a `business` at the portal gets 403 WRONG_PORTAL
          -- its own code, because the only useful response is "your
          side is the app", and the client can only say that if it can
          tell this apart from every other refusal. The check runs AFTER
          the password and BEFORE tokens are issued: checking first
          would let an anonymous caller discover which emails are
          business accounts.

          API keys: auth.api_keys. SHA-256 (not bcrypt -- see the
          model's docstring: 32 bytes of CSPRNG has no dictionary to
          run against it, and a per-request bcrypt on an integration
          endpoint is a self-inflicted DoS). Prefix stored separately so
          a failed attempt names WHICH key. Scoped, revocable, last-used
          tracked with a 5-minute throttle. @api_key_required(*scopes)
          folds authentication and the scope check into one decorator,
          because a route that authenticates a key without declaring
          what it may do is a route every key can reach, and that
          mistake is invisible in review.

        UNCHANGED, as planned: sign-up, OTP, verification, lockout,
        rate limiting.

        TRAPS HIT AND RECORDED
          1. secrets.token_urlsafe draws from an alphabet containing
             "_", which is this key format's own separator. A secret
             holding one would have parsed into four parts and been
             rejected as malformed -- intermittently, depending on the
             random bytes. Switched to token_hex. Caught while writing
             the code, not by a test; the test that now covers it
             asserts the ALPHABET rather than sampling keys, because
             sampling can pass by luck.
          2. The web client read a cookie named csrf_token. The backend
             issues csrf_access_token and csrf_refresh_token. Silent
             401s, forever.
          3. `new RegExp(`(?:^|;\s*)...`)` in a template literal:
             "\s" collapses to a bare "s", so the cookie regex matched
             nothing. Presents as "signed out for no reason".
          4. The web sign-up form collected a phone number that
             registration does not accept, and sent business_name where
             the schema declares data_key "businessName". Both would
             have been dropped in silence. It also missed
             confirmPassword and acceptTerms, which are REQUIRED --
             so sign-up would have 422'd on every attempt.

  KNOWN ENVIRONMENT NOTES
    pytest needs TEST_DATABASE_URL, SECRET_KEY, JWT_SECRET_KEY exported
    manually — Flask's CLI auto-loads .env but pytest does not.

    Do NOT run multiple large domain dirs in one pytest invocation. A ~10-min
    combined run exhausts the Postgres connection pool and produces a wall of
    phantom setup errors. Run one domain dir at a time.

    `flask db migrate` autogenerate surfaces unrelated pre-existing drift.
    Hand-trim generated migrations to the intended change only.

    BaseModel has FIVE columns: id, created_at, updated_at, is_deleted,
    deleted_at. A hand-written migration that omits deleted_at will pass tests
    (conftest uses db.create_all from metadata and never runs migrations) and
    fail in production. This happened once already; see migration
    f2345678901a.

PART 6 — RULES FOR THE V2 WORK
===========================================================================

  1. Do not change approved work while refactoring next to it.
     This was violated once in V1 and cost a full revert. Consistency nobody
     asked for is not a reason to touch a working screen.

  2. Rank in SQL, not Python. Python sorting breaks under pagination.

  3. Tri-state booleans: null is not false.

  4. A thin rail is a broken rail. Under the minimum, render nothing.

  5. Unknown section types render nothing — the server can add a section
     without an app release.

  6. Silence is the honest answer. A section with no data does not appear.

  7. "App boots" proves imports, not that view functions run. Smoke-test the
     actual route.

  8. Never run a write smoke test against the dev database.

  9. Keep the long narrative comments current rather than deleting them. They
     are why V2 could be planned at all.
