CHANGES IN THIS VERSION
--------------------------------------------------------------------------------
REMOVED (never implemented -- documentation only, NO MIGRATION REQUIRED):
    business_questions
    supplier_responses
    Rationale: Business Questions are removed from the product entirely
    (Document 09). These tables were specified in v2.0 of this document
    but were never created in any database. The only migration that has
    ever run is the initial auth domain schema migration, which created
    users, refresh_tokens, otp_verifications, and password_reset_tokens.
    Removing them here is therefore a pure documentation change with zero
    schema impact.

RENAMED (conceptually, documentation only):
    "Supplier Discovery" concepts -> business_suppliers (an explicit
    record of an EXISTING trading relationship).

ADDED (all additive, per TP-014 and TP-040):
    business.business_suppliers
    business.business_customers
    business.credit_ledger_entries
    business.credit_ledger_payments
    supplier.supplier_tiers
    supplier.supplier_staff
    marketplace.payment_events
    marketplace.delivery_confirmations
    platform.sync_queue_events

PRESERVED EXACTLY (implemented, do not modify):
    auth.users, auth.refresh_tokens, auth.otp_verifications,
    auth.password_reset_tokens

================================================================================
1. SCHEMA ARCHITECTURE
================================================================================

The database uses PHYSICAL PostgreSQL schemas, one per business domain,
matching the backend's domain-driven package structure
(backend/src/domains/*).

    auth            Identity, authentication, authorization
    business        Business accounts, suppliers-of-record, customers,
                    credit ledger
    supplier        Supplier accounts, tiers, staff, product catalogue
    marketplace     Orders, deliveries, payments, trade events
    trust           Relationship intelligence and behavioural signals
    verification    Business and supplier verification
    platform        Platform-wide services (notifications, audit,
                    reference data, sync)

Naming note (permitted explicitly): the `marketplace` schema keeps its
name even though TRUConnect is not a marketplace. Internal engineering
names need not match user-facing terminology, and renaming it would
require a disruptive migration for zero user benefit (TP-014: Evolution
Before Replacement).

Schema-qualified foreign keys are required across schema boundaries
(e.g. `auth.users.id`).

================================================================================
2. AUTH SCHEMA  [IMPLEMENTED -- DO NOT MODIFY]
================================================================================

2.1 users
    id, email (unique, lowercase-normalised), password_hash,
    role (enum: business, supplier, admin), first_name, last_name,
    phone_number, account_status (enum: active, suspended, deactivated),
    verification_status (enum: unverified, pending, verified),
    is_active, last_login_at

    One identity per person across the entire TruePoint ecosystem
    (TP-032). Capability is determined by role and permissions, never by
    duplicate user tables.

2.2 refresh_tokens
    id, user_id -> auth.users, jti_hash (unique), expires_at,
    revoked_at, device_id, ip_address

    Stores a hash of the token's JWT ID, never the token. Enables
    rotation and revocation; access tokens remain stateless.

2.3 otp_verifications
    id, user_id -> auth.users, purpose (enum: email_verification,
    phone_verification), destination, otp_code_hash, expires_at,
    attempts, max_attempts, is_used

2.4 password_reset_tokens
    id, user_id -> auth.users, token_hash (unique), expires_at, is_used

2.5 Planned, additive (not yet implemented)
    roles, permissions, role_permissions, user_roles
        Formalises RBAC as data rather than a single role column,
        enabling supplier_staff, supplier_enterprise, and future lender
        roles without new user tables.
    login_history
        Security auditing; also a future risk signal.

================================================================================
3. BUSINESS SCHEMA
================================================================================

3.1 businesses
    id, user_id -> auth.users, business_name, trading_name,
    business_type, industry, years_operating, registered_since,
    is_verified (denormalised from verification)

3.2 business_addresses
    id, business_id, address_line, city_id, province_id, latitude,
    longitude, is_primary

3.3 business_suppliers   [NEW -- the core relationship record]
    id
    business_id -> business.businesses
    supplier_id -> supplier.suppliers   (nullable)
    supplier_name_local        Name as the business knows them
    supplier_phone_local       Contact as the business knows them
    is_on_platform             True once linked to a real supplier account
    invitation_sent_at         (nullable)
    first_recorded_at
    last_order_at              (nullable)
    is_preferred

    PURPOSE: this table IS the repositioning. It records a supplier the
    business ALREADY trades with, whether or not that supplier has ever
    heard of TRUConnect.

    supplier_id is deliberately nullable. A business gets full value from
    day one recording orders against an off-platform supplier; the row is
    later linked when that supplier joins. Without this nullability the
    product would require supplier adoption before delivering business
    value, violating TP-019.

    Constraint: unique on (business_id, supplier_id) where supplier_id is
    not null.

3.4 business_customers   [NEW]
    id, business_id, customer_name, customer_phone (nullable),
    first_recorded_at, last_transaction_at

    PURPOSE: supports the Loan Book. Deliberately minimal -- this is not
    a CRM.

3.5 credit_ledger_entries   [NEW -- the Loan Book]
    id
    business_id -> business.businesses
    customer_id -> business.business_customers
    original_amount
    outstanding_amount
    sale_date
    description                (nullable)
    is_settled
    settled_at                 (nullable)

    PURPOSE: replaces the paper credit book. Records money a CUSTOMER
    owes THIS BUSINESS from a credit sale.

    EXPLICIT SCOPE BOUNDARY: this is record-keeping only. TRUConnect does
    not lend, does not hold funds, and does not collect. It has no
    relationship to any future TruePoint credit product beyond
    contributing behavioural signal (Document 07).

3.6 credit_ledger_payments   [NEW]
    id, credit_ledger_entry_id -> credit_ledger_entries, amount,
    paid_at, note

    Supports partial repayment, which is how informal credit actually
    behaves. outstanding_amount on the parent entry is derived from these.

3.7 business_documents
    id, business_id, document_type, file_url, uploaded_at

3.8 business_settings
    id, business_id, preferred_language, preferred_currency,
    default_delivery_address_id, notification preferences

4. SUPPLIER SCHEMA
================================================================================

4.1 suppliers
    id, user_id -> auth.users, supplier_name, category, contact_number,
    active_since, is_verified

4.2 supplier_tiers   [NEW]
    id, supplier_id -> supplier.suppliers, tier (enum: free, pro,
    enterprise), effective_from, effective_until (nullable)

    PURPOSE: tier history rather than a single mutable column, so
    upgrades and downgrades are auditable (TP-040: historical information
    preserved).

    Current tier = the row where now() falls within the effective range.

4.3 supplier_staff   [NEW -- Supplier Pro]
    id, supplier_id, user_id -> auth.users, staff_role, invited_at,
    accepted_at, is_active

    Staff are ordinary users in auth.users with a supplier_staff role,
    not a separate identity model (TP-032).

4.4 supplier_products   [Supplier Pro]
    id, supplier_id, category_id, name, description, price, unit,
    bulk_pricing_rules, minimum_order_quantity, stock_status,
    is_published

4.5 supplier_product_images
    id, product_id, image_url, sort_order

4.6 supplier_delivery_regions
    id, supplier_id, province_id, city_id, region_description

4.7 supplier_business_hours
    id, supplier_id, day_of_week, open_time, close_time, is_closed

4.8 supplier_updates
    id, supplier_id, update_type, content, published_at, expires_at

================================================================================
5. MARKETPLACE SCHEMA
================================================================================

(Schema name retained; see Section 1.)

5.1 orders
    id
    business_id -> business.businesses
    supplier_id -> supplier.suppliers          (nullable)
    business_supplier_id -> business.business_suppliers
    status (enum: pending, accepted, rejected, in_fulfilment,
            dispatched, delivered, completed, cancelled)
    total_amount
    placed_at, accepted_at, dispatched_at, delivered_at, completed_at,
    cancelled_at
    delivery_address_id -> business.business_addresses
    payment_reference          (nullable)
    is_offline_originated      True if created offline and later synced
    client_generated_id        Idempotency key from the mobile client

    supplier_id is nullable and business_supplier_id is required: an
    order may be recorded against an off-platform supplier for the
    business's own records.

    client_generated_id exists because offline sync WILL retry. Without a
    client-side idempotency key, a retried sync creates duplicate orders
    -- a correctness failure the business would experience as a real
    duplicate delivery.

5.2 order_items
    id, order_id, product_id (nullable), item_name_text, quantity, unit,
    unit_price_at_order_time, line_total

    product_id is nullable and item_name_text is always present:
    Supplier Free has no catalogue, so items are free text. Supplier Pro
    orders reference real products.

5.3 payment_events   [NEW]
    id, order_id -> orders, event_type (enum: reference_issued,
    payment_marked_sent, payment_confirmed), amount, reference,
    recorded_by_user_id, occurred_at

    PURPOSE: records that a payment happened, between the parties,
    directly. TRUConnect NEVER holds funds and is not in the payment
    path. This is an event log, not a ledger of platform-held money
    (Constitution: TRUConnect is not a money holder).

5.4 delivery_confirmations   [NEW]
    id, order_id, confirmed_by_user_id, confirmed_by_role, confirmed_at,
    note

    PURPOSE: replaces "he said it was delivered" with a timestamped
    record from a known party. Directly reduces the most common informal
    trade dispute.

5.5 saved_products
    id, business_id, product_id, created_at

    The fundamental unit of trust (Document 07). Distinct from

6.3 trust_signals
    id, owner_type, owner_id, signal_type, signal_value, calculated_at

    id, business_id, score, calculated_at, methodology_version

6.5 supplier_reputation_scores
    id, supplier_id, score, calculated_at, methodology_version

6.6 trust_score_history
    id, owner_type, owner_id, score_type, score_value, recorded_at

Note: these scores are TRUConnect-internal operational indicators and
INPUTS to a future platform-level TRUScore. They are not credit scores
and must never be presented as such (Document 07).

    without server-side sync accounting it cannot be operated or debugged
    at scale.

================================================================================
9. DESIGN NOTES
================================================================================

    1. All monetary values use fixed-point decimal, never floating point.
    2. Soft deletes preserve trust-relevant history (TP-040).
    3. Every schema change is additive. Nothing implemented is dropped or
       renamed (TP-014, TP-043).
    4. business.business_suppliers is the single most important new
       table: it encodes "relationships already exist" directly into the
       data model.
    5. Nullable supplier_id (orders, business_suppliers) is a deliberate
       architectural decision enabling independent business value
       (TP-019), not an oversight.
    6. client_generated_id on orders is a correctness requirement for
       offline sync, not an optimisation.

================================================================================
10. FUTURE (OUT OF TRUCONNECT SCOPE)
================================================================================

Wallet, credit application, and lending tables are NOT part of
TRUConnect's database. They belong to future TruePoint products
(TRUWallet, TRUPayLater) and will consume trust schema outputs through
platform APIs rather than sharing TRUConnect's operational tables.

This is a change from earlier versions of this document, which reserved
wallet and credit tables inside TRUConnect. TRUConnect is not a money
holder (Constitution).
