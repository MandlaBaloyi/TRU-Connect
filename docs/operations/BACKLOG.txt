===========================================================================
BACKLOG — WHAT IS OUTSTANDING, AND HOW URGENT
===========================================================================

Started 2026-09-11. An INDEX, not a plan. Each line says what and why
now; the reasoning lives in the document named beside it.

WHY THIS FILE EXISTS. Working on one thing surfaces three others --
writing the verification plan revealed that the media path would make
ID documents world-readable; building the curtain revealed that 325
test fixtures encoded an assumption; testing a banner revealed there
was no approval email at all. None of that was foreseeable from the
start, and none of it belonged in the task that found it. An idea
arriving mid-task needs somewhere to go that is not somebody's memory.

  ─────────────────────────────────────────────────────────────────────
  THE TRIAGE QUESTION IS NOT "IS THIS A GOOD IDEA".
  Almost everything here is. It is: DOES WAITING MAKE IT COST MORE?
  ─────────────────────────────────────────────────────────────────────

That is the only thing the two sections below distinguish. A trigger
("the first supplier who asks for a second login") beats a date,
because a date slips quietly and a trigger cannot.

HOW TO USE IT. Add a line when something surfaces; delete it when it
ships. If an entry needs more than two lines, it needs a document, and
this file should point at that document instead.

A — GETS MORE EXPENSIVE THE LONGER WE WAIT
===========================================================================

These are the only entries with a claim on the present.

  A1  IDEMPOTENCY KEYS ON POST                          V2_13 §3.1
      An ERP times out and retries -- correctly, since it cannot know
      whether we processed it -- and we create a second product.
      WHY NOW: the habit is the expensive part, not the table. Two
      years of write endpoints built without one means revisiting
      every single endpoint and re-deciding what "the same request"
      means for each.

  A2  AN EVENT LOG FOR STOCK ORDERS                     V2_13 §3.2
      network/orders/models/ has stock_order and stock_order_payment
      and no event record; the business's own books have two
      (LoanHistoryEvent, OrderHistoryEvent).
      WHY NOW: webhooks replay from an event stream, and the rows
      cannot be backfilled for history never recorded. Also answers
      "why did this order change?" today, which is a support question
      currently answered by inference.

  A3  THE ORIGIN OF A WRITE                             V2_13 §3.3
      No `source` (APP / IMPORT / API) on stock, price or product
      writes.
      WHY NOW: a column added later starts null for every existing
      row, and no analysis recovers where a number came from two years
      ago. Useful immediately: "how many of this supplier's prices were
      typed by hand?"

  A4  ACCOUNT DELETION -- DECIDE ondelete WHEN ADDING A FOREIGN KEY
                                                    V2_07, CLEANUP
      RESCOPED 2026-09-11 after measuring it. The old entry said
      "account deletion does not work cleanly across ten tables",
      which is true and points at the wrong problem.

      WHAT IS ACTUALLY THERE: 43 tables, 52 foreign keys, and 41 of
      those 52 are NO ACTION. That is not a policy anybody chose --
      it is SQLAlchemy's default, applied by omission. auth.users is
      referenced by 20 tables directly, supplier_profiles by 10,
      supplier_offers by 8.

      SO IT IS A CLASSIFICATION PROBLEM, NOT A CASCADE BUG. The same
      mechanism needs opposite answers:
        loan_book_customers          CASCADE  (a shop's private notes)
        stock_orders.buyer_name      SET NULL + scrub (the order must
                                     survive for accounting; the name
                                     need not)
        match_reviews.decided_by     RETAIN   (who approved a
                                     catalogue alias outlives the
                                     staff account)
      CASCADE on the last would erase the audit story; NO ACTION on
      the first makes deletion impossible. No foreign key can express
      that -- it is per-table judgement.

      AND THERE ARE TWO ROLES, WHICH ARE TWO DIFFERENT PROBLEMS:

        BUSINESS (8 tables) touches THIRD PARTIES. loan_book_customers
        and order_book_customers hold names and phone numbers of the
        SHOP's customers -- people who never signed up to TruConnect
        and never consented to us. We have no analytical claim on
        them at all, which makes this the easy half: delete.

        SUPPLIER (8 tables) touches the SHARED CATALOGUE, and is the
        hard half. GOOD NEWS FOUND WHILE CHECKING: match_aliases has
        no foreign key to a supplier -- only to catalogue.products --
        so the learned aliases survive a supplier deletion already.
        The shared learning is genuinely shared rather than owned by
        whoever taught it. match_reviews does reference
        supplier_offers and auth.users, so the decision history is
        the part that needs a rule.

        BOTH (3 tables) need each side's answer to be compatible:
        stock_orders, connection_requests, supplier_reports. A
        stock order has a buyer AND a seller; deleting either must
        not erase the other's record of the trade.

      WHY IT IS NOT SCHEDULED: the table count is still moving, and
      41 undecided keys is 41 judgements that cannot be mechanically
      derived. Deciding them now would mean redoing it as tables are
      added.

      WHAT TO DO INSTEAD, AND IT IS CHEAP: when a NEW table gets a
      foreign key to users (or to a profile), choose its ondelete
      deliberately and say why in a comment. Ten seconds while
      writing the model; 41 archaeological digs otherwise. The
      eventual deletion work then becomes READING decisions rather
      than MAKING them.

      Soft-delete coverage is already good: 39 of 43 tables have
      is_deleted, and the four without (audit_events, the two
      history-event tables, notifications) are append-only by design
      and should stay that way. Exactly one table holds personal data
      without soft-delete -- security.audit_events (email, IP, user
      agent) -- and that tension is real: the record proving who
      approved a supplier cannot be erased on request. A shorter
      retention window on that table specifically is the likely
      answer, not an exemption forever.

  THE CATALOGUE, ONCE IT HAS REAL DECISIONS IN IT
  B11 ORDER THE REVIEW QUEUE BY WHAT IT UNLOCKS, not by confidence.
      Today: match_review_repository.list_pending orders by
      confidence DESC, with the stated aim that "the queue gets
      shorter fastest from that end".

      THAT OPTIMISES THE WRONG THING. Accepting a review writes a
      GLOBAL alias -- the next supplier who types those words matches
      for free, forever -- so the objective is "future rows resolved
      per human decision", and confidence is a poor proxy for it. A
      confident match on a product one supplier sells unlocks nothing;
      an ambiguous one on a staple forty suppliers spell differently
      unlocks forty.

      Noticed 2026-09-12 by analogy with the Entelect Hack<IT>
      challenge (Mandla's plant-ecosystem-optimizer): a fast-spreading
      species monopolises the grid and shades out the ones that unlock
      cascades, so the winning move was to reorder rather than to
      work harder. Same shape here -- the high-confidence match is
      the aggressive spreader.

      TRIGGER: enough real accept/reject decisions to measure against.
      The queue is empty today, so there is nothing to reorder and no
      way to know whether a reorder helped.

  B12 FIT THE TWO MATCHING THRESHOLDS instead of picking them.
      MATCHING_AUTO_LINK_CONFIDENCE (0.92) and
      MATCHING_REVIEW_CONFIDENCE (0.70) are hand-chosen. MatchReview
      .evidence already records brand_agrees, pack_agrees,
      text_similarity and candidates_considered, so accumulated human
      decisions become a labelled set those thresholds can be fitted
      against -- wrong auto-links are expensive, a long queue is
      expensive in a person's time, and the balance between them is
      measurable rather than guessed.

      AND A WARNING THAT CAME WITH THE ANALOGY: a hard threshold is a
      CLIFF. In the hackathon, one species landing at 1.5% against a
      2% requirement collapsed the result from 28 species to 6. 0.92
      is the same kind of edge -- a near-miss behaves completely
      differently from a near-hit, silently. Worth knowing that is a
      property we have, not only something that bit somebody else.

      TRIGGER: same as B11.

      NOT A CREDIT-RISK MODEL. The obvious-sounding version of this
      idea -- portfolio diversification for lending -- does not apply:
      TruConnect does not lend. The Loan Book is a shop's record of
      ITS OWN customers' credit and V2_03 §3.3 is explicit that we
      cannot verify it. There is no capital, no portfolio and no
      default data to fit anything to. Recorded here so the analogy is
      not mistaken for a roadmap item later.

  B14 INHERIT A CATEGORY FROM THE PRODUCT AN OFFER MATCHED TO.
      The importer NORMALISES a category ("beverages" -> BEVERAGES via
      match_category) but deliberately refuses to INFER one: an
      unmatched category errors the row, and fields.py says why -- a
      product filed under the wrong category is worse than an honest
      error, because it lands somewhere nobody looks.

      THE MISSING HALF IS ALREADY PAID FOR. The matching ladder links
      an offer to a catalogue product, and catalogue products carry
      their own category. So a blank category can be INHERITED from
      the row it resolved to rather than guessed from its text -- not
      inference, and not a weakening of the rule in fields.py: the
      link was already earned through barcode, alias or normalised
      matching before the category is read off it.

      Only applies at tiers 0-3. An AI-tier match should NOT silently
      set a category the supplier never typed.

  B15 ASK CLOUDINARY INSTEAD OF GIVING UP ON IT.
      stuck_media_sweep marks a row ERROR when it has sat PENDING for
      30 minutes -- correct as far as it goes, because this backend
      never learned the asset failed a scan, only that it never heard
      back. But a missing WEBHOOK is not a missing ASSET: the image is
      sitting in Cloudinary with a moderation status we could simply
      read.

      So the job should reconcile before it condemns -- query the
      provider, and only mark ERROR when the provider itself has
      nothing. RECONCILIATION, NOT RETRY: there is nothing to retry
      here, the upload already succeeded.

      Fits the existing job contract exactly (pure run() -> JobResult
      in shared/media/jobs/, a JobSpec in media_scheduler.py). About an
      hour.

  B16 AN UPLOAD QUEUE ON THE DEVICE, SURVIVING APP CLOSE.
      The other half of B15, and the half no scheduler can ever do:
      when an upload dies mid-flight the bytes are on the phone and
      Cloudinary never saw them. No server job can retry an upload it
      did not receive. Only the app can.

      So this is a local queue -- record the intent, hold the file,
      retry when signal returns, survive the app being killed. It
      belongs with the offline write-path work rather than on its own,
      because it needs the same local-first storage decision and would
      otherwise be that decision made twice.
