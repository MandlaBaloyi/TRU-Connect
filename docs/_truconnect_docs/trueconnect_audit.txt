================================================================================
TRU CONNECT
SECURITY DOMAIN
PHASE 1 - ENTERPRISE AUDIT ARCHITECTURE PLAN
================================================================================

OBJECTIVE

Build an enterprise-grade auditing backend that becomes the single source of
truth for every security-related event occurring throughout the TRU Connect
ecosystem.

For Phase 1, only the Authentication domain will integrate with the Security
domain.

The architecture, however, must be designed from day one to support every
future domain without requiring redesign.

The Security domain is NOT part of Authentication.

Authentication simply publishes security events.

The Security domain owns:

• Security Auditing
• Security Monitoring
• Security Analytics
• Threat Detection
• Compliance
• Incident Investigation
• Regulatory Audit Trails
• Security Intelligence

================================================================================
ARCHITECTURE PHILOSOPHY
================================================================================

Authentication is responsible for authentication.

Security is responsible for auditing.

Authentication should never know how audit data is stored.

Instead, Authentication simply publishes events.

Example

Authentication
      │
      ▼
Security Audit Service
      │
      ▼
Audit Repository
      │
      ▼
PostgreSQL (security schema)
      │
      ▼
Detection Engine
      │
      ▼
Security Alerts
      │
      ▼
Admin Control Center

This separation keeps the Authentication domain clean while allowing the
Security domain to evolve independently.

================================================================================
ENTERPRISE AUDIT PRINCIPLES
================================================================================

The audit system should answer the following questions for every important
system action:

Who performed the action?

When did it occur?

Where did it originate?

What action was performed?

Was it successful?

Why did it fail?

What happened afterwards?

Every audit record must be append-only.

Audit records should never be modified.

Audit records should never be deleted manually.

Historical integrity is essential for regulators, investigations and compliance.

================================================================================
AUDIT EVENT MODEL
================================================================================

The audit model must remain generic.

It must never contain Authentication-specific assumptions.

Recommended fields include:

Audit Event ID

Timestamp (UTC)

Domain

Module

Event Name

Event Category

Severity

Status (Success/Failure)

Failure Reason

User ID (nullable)

Email

Role

Tenant ID

Session ID

Correlation ID

Request ID

IP Address

User Agent

Browser

Operating System

Platform

Device ID

HTTP Method

Endpoint

HTTP Status Code

Metadata (JSON)

The Metadata field allows future domains to store additional information without
requiring database redesign.

================================================================================
DETECTION RESPONSIBILITY
================================================================================

Authentication should never contain security intelligence.

Bad Example

if failed_logins >= 5:
    lock_account()

Good Example

Authentication

↓

Publish Audit Event

↓

Security Detection Engine

↓

Evaluate Rules

↓

Create Alert

↓

Notify Administrator

↓

(Optional) Lock Account

The Security domain owns all detection logic.

================================================================================
DATABASE DESIGN
================================================================================

Do NOT create separate audit tables for every domain.

Avoid:

auth_audit

supplier_audit

wallet_audit

business_audit

Instead create a single enterprise audit table.

Example

audit_events

Every row identifies its origin using fields such as:

Domain

Module

Event

This allows every domain to share the same enterprise audit platform.

================================================================================
ENGINEERING GOAL
================================================================================

The Security domain should become the enterprise Security Operations Center
(SOC) for TRU Connect.

Every important action performed anywhere within the platform should eventually
produce a standardized audit event.

The Authentication domain is simply the first publisher.

Future domains should integrate seamlessly by publishing events to the same
Security infrastructure.

The final architecture must remain modular, scalable, regulator-friendly,
enterprise-ready and maintainable for long-term growth.
