DECISIONS GOVERNING THIS PASS
--------------------------------------------------------------------------------
1. Business Questions / Business Conversations: REMOVED ENTIRELY.
2. Supplier Discovery: RETAINED as a small, late-phase (Stage 5) feature.
3. Loan Book: tracks CUSTOMERS who owe THE BUSINESS (credit sales).

--------------------------------------------------------------------------------
GLOBAL COMPATIBILITY STATEMENT
--------------------------------------------------------------------------------
NO BACKEND REWRITE IS REQUIRED BY THIS DOCUMENTATION PASS.

    - The auth domain is untouched. All nine implemented endpoints are
      documented exactly as built.
    - Removing business_questions and supplier_responses requires NO
      migration: they were documented in v2 but never created. The only
      migration ever run created users, refresh_tokens,
      otp_verifications, password_reset_tokens.
    - All new tables are additive.
    - The `marketplace` schema keeps its name.
    - The implemented mobile navigation (5 tabs per role) is unchanged;
      only tab CONTENT is re-specified.
    - The notification infrastructure is unchanged.

DOCUMENT 00 -- PROJECT VISION
================================================================================

1. CURRENT ASSUMPTIONS
   Thesis: "helps businesses discover trusted suppliers". Problem framed
   as sourcing difficulty and supplier-comparison difficulty. Success
   measured partly by credit-product uptake.

2. PROBLEMS
   The founding clause is wrong under the Constitution. Businesses
   already know their suppliers (TP-055). Framing the problem as
   discovery misdirects every downstream document. Credit-uptake metrics
   violate TP-084.

3. MODIFICATIONS
   Problem restated as operational friction (WhatsApp/phone/paper) and
   commercial invisibility. Competition explicitly named. Supplier tiers
   introduced. Explicit "What TRUConnect Is Not" section. Success metrics
   rebuilt around operational adoption and trust formation.

4. NEW STRUCTURE
   Constitutional alignment header; Problem; Vision; Mission; Users
   (Business Free primary, Supplier Free/Pro/Enterprise); Core
   Philosophy; Why Informal Businesses; Why Suppliers; Why Trust Before
   Lending; What TRUConnect Is Not; Success Metrics.

5. COMPATIBILITY IMPACT
   None. Vision document; no code dependency.

6. MIGRATION NOTES
   None.

7. FUTURE EXTENSIBILITY
   User tiers and ecosystem stages are named explicitly, so future
   products slot in without restating the vision.

DOCUMENT 01 -- PRODUCT SPECIFICATION
================================================================================

1. CURRENT ASSUMPTIONS
   A "Supplier Discovery Module" (search, categories, nearby, featured,
   popular, recently viewed) as a core tab. Business Questions as a core
   module. No tier concept. Wallet as a business feature.

2. PROBLEMS
   The Suppliers tab was a marketplace browse surface. Business Questions
   assumed unknown suppliers. Tiers absent entirely. Wallet violates the
   money-holder prohibition.

3. MODIFICATIONS
   "Supplier Discovery" -> "My Suppliers". Business Questions removed.
   Added: Order Queue, Loan Book, Customers, Offline Support, supplier
   tiers. "Add My Suppliers" established as the defining first action.
   Wallet removed. Discovery demoted to Stage 5, inside the Discovery
   tab.

4. NEW STRUCTURE
   Philosophy; Overview; User Tiers; Business Journey; Supplier Journey;
   Navigation (aligned to implemented tabs); Features (each with problem
   solved); Screens; Roles; Design Principles; Future Expansion.

5. COMPATIBILITY IMPACT
   Navigation structure unchanged -- existing tab layouts remain valid.
   Existing frontend feature folders (find-supplier, nearby-suppliers,
   recommended-products) are re-scoped to Stage 5 rather than deleted;
   they contain no implementation yet.

6. MIGRATION NOTES
   No code migration. Frontend folders may be renamed at implementation
   time; none currently contain code.

7. FUTURE EXTENSIBILITY
   Tiers map to RBAC permissions, so Pro/Enterprise capability arrives
   without structural change.

DOCUMENT 04 -- DATABASE DESIGN
================================================================================

1. CURRENT ASSUMPTIONS
   Logical domains within the public schema. business_questions and
   supplier_responses tables. Reserved wallet/credit tables.

2. PROBLEMS
   The database now uses PHYSICAL schemas per domain (auth, business,
   marketplace, platform, supplier, trust, verification), so the document
   no longer described reality. Question tables belong to a removed
   feature. Wallet/credit tables violate the money-holder prohibition.

3. MODIFICATIONS
   Documented the real physical schema architecture. Removed question
   tables and wallet/credit reservations. Added: business_suppliers,
   business_customers, credit_ledger_entries, credit_ledger_payments,
   supplier_tiers, supplier_staff, payment_events,
   delivery_confirmations, sync_queue_events. Added nullable supplier_id
   and client_generated_id to orders.

4. NEW STRUCTURE
   Schema architecture; auth (implemented); business; supplier;
   marketplace; trust; verification; platform; design notes; out of
   scope.

5. COMPATIBILITY IMPACT
   Zero impact on implemented tables. All changes additive.

6. MIGRATION NOTES
   - Removing business_questions/supplier_responses: NO MIGRATION. Never
     created.
   - New tables: standard additive migrations when each feature is built.
   - orders.client_generated_id must be indexed and unique per business
     to enforce sync idempotency.
   - marketplace schema NOT renamed; renaming would be a disruptive
     migration for zero user benefit.

7. FUTURE EXTENSIBILITY
   Nullable supplier_id enables off-platform suppliers permanently.
   supplier_tiers as history (not a column) makes tier changes auditable.
   Formal RBAC tables are specified as additive for future roles.

DOCUMENT 07 -- DATA AND TRUST ENGINE
================================================================================

1. CURRENT ASSUMPTIONS
   Business Question engagement as a trust signal. "Future Credit
   Readiness" as a TRUConnect concept.

2. PROBLEMS
   Question signals reference a removed feature. Credit-readiness inside
   TRUConnect violates TP-084. The document did not distinguish
   bilaterally confirmed data from self-reported data -- the single most
   important distinction in the trust model.

3. MODIFICATIONS
   Removed question signals and credit-readiness framing. Added a
   dedicated section on why bilateral confirmation is what makes the data
   trustworthy. Added delivery, payment, and credit-ledger signals, with
   the Loan Book explicitly weighted lower as self-reported and
   privacy-restricted. Scores reframed as operational indicators and
   TRUScore inputs.

4. NEW STRUCTURE
   Constitutional sequence; Overview; Why this data is trustworthy;
   Business profile; Supplier profile; Relationship intelligence;
   Behavioural signals; Trust vs risk; Scoring methodology; Relationship
   to TRUScore; AI (future); Data ownership.

5. COMPATIBILITY IMPACT
   None. Trust schema tables unchanged.

6. MIGRATION NOTES
   None. methodology_version already exists on score tables.

7. FUTURE EXTENSIBILITY
   The self-reported vs confirmed distinction is now explicit, so future
   signals inherit correct weighting discipline.

   Built around Business Conversations as the core differentiator, with
   extended argument for public Q&A over star ratings.

   Rewritten around: why not a marketplace; who we actually compete with;

   tiers; why relationships; why bilateral confirmation is the real moat;
   why TRUConnect never touches money.

   Relationships; Bilateral confirmation moat; No money custody; Trust

6. MIGRATION NOTES
   None.

7. FUTURE EXTENSIBILITY
   The seven-question governing test gives future teams a concrete filter

================================================================================
OPEN ITEMS FOR THE PRODUCT OWNER
================================================================================

1. Community tab
   Not named in the Constitution's feature lists and not clearly tied to
   an operational problem. It exists in the implemented navigation. It is
   documented here as low-priority and non-commercial, but it should be
   explicitly justified against the governing test (Document 09,
   Section 13) or scheduled for removal.

2. Frontend feature folders
   find-supplier, nearby-suppliers, and recommended-products exist as
   empty scaffolding under features/dashboard/business. Under the revised
   model these are Stage 5 concerns. They currently contain no code;
   recommend leaving them empty rather than building against them.

3. Supplier invitation channel
   Invitations require SMS or WhatsApp to be effective, since off-platform
   suppliers are unlikely to be reached by email. The notification
   infrastructure currently supports email only. This is a Stage 2
   dependency and should be planned before supplier invitations ship.

4. Loan Book customer consent
   Loan Book entries record third parties (the business's customers) who
   are not platform users. The current design keeps this data strictly
   private to the owning business, which is the correct default. Confirm
   this satisfies your POPIA position before Stage 1 ships.
